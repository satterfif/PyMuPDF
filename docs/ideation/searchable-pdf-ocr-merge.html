Searchable PDF — merging OCR JSON onto image PDFs

Ideation · repo-grounded · PyMuPDF

Generated 2026-07-28 · Subject: a PyMuPDF tool that overlays an invisible OCR text layer (from Dynamics/Azure OCR JSON) onto an image-only PDF page to make it searchable.

The problem in one line

You have image-only PDF pages (page_005.pdf) and matching OCR results as JSON (page_005_formatted.json) with line-level text and normalized (0–1) bounding boxes. You want final_page_005.pdf: the same image, plus an invisible, selectable, searchable text layer aligned to the page.

Grounding context

  • JSON shape (page_005_formatted.json): Dynamics CRM expando wrapper → top-level array; each element has page, fullPageText, and lines[]. Each line = text + boundingBox (left/top/width/height as 0–1 fractions, top-left origin, plus a 4-point polygon). No word-level boxes. 107 lines on page 5; OCR text is noisy (e.g. "Salte / page"). Text includes non-ASCII (Österreich, prüfzeugnis).
  • Sibling files: a whole pages/ directory of page_NNN.pdf + page_NNN(_formatted).json pairs — naming is inconsistent (page_001.json vs page_005_formatted.json).
  • PyMuPDF capability: render_mode=3 emits 3 Tr = invisible text (confirmed src/__init__.py:15524). TextWriter (16905) + write_text(page, render_mode=3) (17254) is the scalable path; supports opacity/color. Python API uses top-left origin — matches Azure coords, no y-flip needed. overlay=True keeps the image untouched.
  • Existing convention to mirror: scripts/pdf_splitter_cli.py — argparse, SplitterError, --json output, path validation, thread pool for I/O.
  • Topic axes: (1) text-layer technique · (2) normalized→PDF coordinate mapping · (3) text-fit & quality · (4) CLI & batch integration · (5) robustness to schema/OCR variance.

How the core approach works

  OCR JSON (normalized, top-left)          PDF page (points, W×H)
  ┌─────────────────────────────┐          ┌─────────────────────────────┐
  │ line "Customer Name"        │          │  (scanned image, untouched)  │
  │  left=0.021 top=0.012       │          │                              │
  │  width=0.130 height=0.014   │  ──────► │  x  = left * W               │
  │  text="Customer Name"       │  map     │  y0 = top  * H  (box top)    │
  └─────────────────────────────┘          │  baseline = (top+height)*H   │
                                            │  fontsize = height * H       │
       for each of 107 lines               │  Tz = box_w / natural_w      │
              │                             │                              │
              ▼                             │  TextWriter.append(pt, text) │
   TextWriter.write_text(page,             │        ▼                     │
        render_mode=3)  ── 3 Tr ──►        │  invisible glyphs, selectable│
                                            └─────────────────────────────┘
   Result: final_page_005.pdf — image you SEE, text you SEARCH.

Font sized from box height, then horizontally scaled so the invisible string spans the box width — this makes selection/highlight track the printed image without needing word boxes.

Top candidates

1

Invisible per-line text layer via TextWriter

technique
IdeaFor each OCR line, place its full text as one invisible run (render_mode=3) at baseline = box bottom, fontsize ≈ height*H. Accumulate all 107 lines in one TextWriter and emit once with write_text(page, render_mode=3). The image is preserved (overlay=True).
Why it winsThe canonical "OCR sandwich" used by Tesseract/OCRmyPDF. One content stream, one Tr 3, scales to hundreds of lines. Selectable + searchable with copy/paste fidelity.
Open question for brainstormWidth-fit: adjust fontsize down vs. apply horizontal scaling (Tz) so the run matches box width. TextWriter returns the cursor so overflow is measurable.

Basis: internal:src/__init__.py:16905,17254,15524 · external: OCRmyPDF glyphless-font renderer, PyMuPDF recipes-ocr.

2

Standalone CLI tool mirroring pdf_splitter_cli.py

integration
Ideascripts/ocr_merge_cli.py: given a PDF + JSON, write final_<name>.pdf. OcrMergeError, --json output, path validation — same shape as the splitter. Add a directory/batch mode that pairs every page_NNN.pdf with its JSON and produces all final_*.pdf in one run.
Why it winsFits the documented "standalone scripts, not part of the wheel" pattern; Power-Automate-friendly JSON output; reuses the proven threaded I/O structure.

Basis: internal:scripts/pdf_splitter_cli.py:1-279 · CLAUDE.md splitter tooling section.

3

Coordinate-mapping module (normalized → PDF points)

coord-map
IdeaA small pure-function core: (norm_bbox, page.rect, page.rotation) → insertion Point + fontsize. Handles top-left origin (no flip), baseline offset, and /Rotate pages via derotation_matrix. Independently unit-testable with synthetic boxes — no PDF needed.
Why it winsIsolates the one part most likely to be wrong (off-by-a-flip, rotation) into testable pure code. Everything else composes around it.

Basis: internal:src/__init__.py:15485,11141,13039 · external: Azure Read coord convention.

4

OCR-JSON schema adapter (Dynamics expando parser)

robustness
IdeaA tolerant loader that strips @odata.type noise, extracts lines[].text + boundingBox, and normalizes the input regardless of page_NNN.json vs page_NNN_formatted.json naming. Skips empty/whitespace lines and clamps out-of-range coordinates.
Why it winsDecouples the fragile vendor format from the rendering logic; makes it trivial to support a second OCR source later. Guards against the real naming inconsistency seen in pages/.

Basis: internal: observed JSON in pages/*.json · directory listing naming mismatch.

5

Unicode font embedding for non-ASCII OCR text

quality
IdeaUse a Unicode-capable embedded TTF in the TextWriter instead of base-14 helv, so accented/German characters (Österreich, prüfzeugnis) copy/paste and search correctly with a proper ToUnicode map. Fall back gracefully on glyphs the font lacks.
Why it winsThe sample data is literally full of non-ASCII; helv would drop or mangle it, silently breaking search — the whole point of the feature.

Basis: external: ToUnicode/encoding gotchas (PyMuPDF textwriter, Azure Read).

6

Visual QA / --debug overlay mode

qualitytestability
IdeaA flag that renders the text visibly (render_mode=0, red, semi-transparent) plus box outlines, so a human can eyeball alignment before trusting the invisible layer. Also a golden-file test: extract text from final_*.pdf and assert coordinates land within tolerance of the source boxes.
Why it winsAlignment bugs are invisible by construction — mode 3 hides exactly what you need to verify. Both scouts independently flagged "render visible first, then switch to 3."

Basis: external: both research agents' validation recommendation.

7

Word-level proportional distribution (stretch)

techniquestretch
IdeaSince the JSON has no word boxes, split each line into words and distribute them across the line box by measured character advance — giving tighter per-word selection highlights.
Why it's a stretch, not a baseLine-level placement already yields full search; per-word is a polish that adds real complexity. Build only if selection granularity matters.

Basis: external: line-vs-word tradeoff (research §2) · internal:src/__init__.py:8502 (Font.text_length).

Considered and rejected

  • insert_textbox auto-fit per line — layout-driven wrapping destroys the 1:1 line→position correspondence that makes selection track the image. The width-fit idea survives (folded into candidate 1); the wrapping textbox does not.
  • Polygon / skew correction via morph — the sample boxes are near axis-aligned; handling the 4-point polygon and page skew is real work for marginal gain. Defer past v1.
  • Pixmap.pdfocr_save() (built-in Tesseract path) — re-runs OCR and ignores your existing Azure JSON. Wrong tool: you already paid for the OCR results.
  • Positioned fullPageText as the primary source — it's one blob with no per-line geometry; useful only as a last-resort "at least it's searchable" fallback, not a direction.

Suggested next step

Candidates 1–4 together form the natural v1 (invisible layer + CLI + coord map + schema adapter), with 5 as a correctness must-have for this data and 6 as the way to trust it. A good handoff to ce-brainstorm would be candidate 1 (the layer technique) or the CLI shape — deciding the width-fit strategy and the single-page-vs-batch surface precisely enough to plan.
